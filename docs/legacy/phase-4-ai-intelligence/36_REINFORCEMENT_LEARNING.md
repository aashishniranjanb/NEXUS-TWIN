# 36 — Reinforcement Learning (Optional / Phase 2 Stretch Goal)

## Status
**Not a dependency for the core prototype.** This document exists so that, if time allows after `35_STRATEGY_OPTIMIZATION.md`'s deterministic scorer is working end-to-end, the team has a scoped plan for an RL upgrade — and so judges see the team has thought about it deliberately rather than avoided it.

## Why RL Is Deferred (Not Abandoned)

- Training an RL agent reliably within an 8-hour build window is high-risk: convergence, reward shaping, and debugging a learned policy live are all time-expensive.
- The deterministic multi-objective scorer (`35_STRATEGY_OPTIMIZATION.md`) already gives a working, explainable, network-aware decision mechanism — RL would need to demonstrably improve on it to be worth the risk, not just be "more advanced" for its own sake.
- Existing 2026 research already demonstrates RL-based (and GNN+LSTM+Transformer+RL) traffic control extensively (`04_RESEARCH_LITERATURE.md`) — RL alone is not part of our novelty claim (`07_NOVELTY_AND_CONTRIBUTIONS.md`).

## Scoped RL Design (If Attempted)

### Environment
- The Digital Twin (SUMO via TraCI) serves as the RL environment, consistent with prior art (`04_RESEARCH_LITERATURE.md`, refs 3–4).

### State
- The same `NetworkState` used elsewhere (`25_TRAFFIC_STATE_MODEL.md`), possibly reduced to a fixed-size feature vector.

### Action Space
- Discrete: select one of the candidate strategy types generated by `34_STRATEGY_GENERATION.md` (keeps the action space small and directly comparable to the deterministic scorer — same candidates, different selection mechanism).

### Reward
- Negative of the same scoring function used in `35_STRATEGY_OPTIMIZATION.md`:
  ```text
  reward = -1 * score(chosen_candidate_metrics, weights)
  ```
  This keeps the RL agent optimizing for exactly the same network-level objective as the deterministic baseline, making an apples-to-apples ablation possible (`44_ABLATION_STUDY.md`).

### Algorithm
- A simple, well-supported algorithm (e.g., DQN for the discrete action space) rather than a complex actor-critic setup, to maximize the chance of getting *something* trained and working in limited time.

### Training Loop (sketch)

```text
for episode in range(N):
    reset Twin to a randomized starting scenario (09_USE_CASES.md)
    for step in range(max_steps):
        state = get_network_state()
        candidates = generate_candidates(state)         # 34
        action = agent.select(state, candidates)
        metrics = scenario_engine.evaluate([action])    # 27
        reward = -score(metrics, weights)                # 35
        agent.update(state, action, reward, next_state)
        apply(action)
```

## Evaluation If Implemented
- Compared directly against the deterministic scorer as an **ablation** (`44_ABLATION_STUDY.md`: "Full NexusTwin [deterministic] vs. + RL"), not presented as a wholesale replacement unless it clearly outperforms.

## Decision Rule
> Attempt RL only after: (a) Phase 3 is fully tested (`30_SIMULATION_TESTING.md`), (b) the deterministic optimizer (`35_STRATEGY_OPTIMIZATION.md`) is working and demoable end-to-end, and (c) meaningful time remains in the build window. If any of these aren't true, skip RL and rely on the deterministic scorer — this is a legitimate, defensible choice, not a shortfall, per the scope discipline in `10_SCOPE_AND_NON_SCOPE.md`.
